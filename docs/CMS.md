# CMS guide (Outstatic)

This site uses **[Outstatic](https://outstatic.com)** (v2) as its CMS. Outstatic is a Git-based CMS that runs **inside this Next.js app**. There is no separate server or database. Content is stored as Markdown/MDX files in this repository, and every save in the CMS creates a commit on GitHub.

- Outstatic docs: <https://outstatic.com/docs>
- Environment variable reference: <https://outstatic.com/docs/environment-variables>

---

## CMS URL

| Environment | URL |
|---|---|
| Local | <http://localhost:3000/outstatic> |
| Production | `https://www.happyhomescommunity.org.uk/outstatic` (once v2 is deployed to that domain) |

The CMS lives at `<your app URL>/outstatic`. You log in with **GitHub**, and your account needs write access to `Happy-Homes-Community/happy-homes-community-v2`, because Outstatic commits to the repo as you.

## How it's wired up

| File | Purpose |
|---|---|
| `app/(cms)/outstatic/[[...ost]]/page.tsx` | Renders the Outstatic admin UI at `/outstatic/*` |
| `app/(cms)/layout.tsx` | Separate root layout for the CMS so the site's Navbar/Footer/theme don't wrap the admin UI |
| `app/api/outstatic/[[...ost]]/route.ts` | Outstatic's API routes (GitHub OAuth login, callback, etc.) at `/api/outstatic/*` |
| `app/lib/contentParser.ts` | `getPageData()`, a typed wrapper around `getDocumentBySlug` from `outstatic/server` |
| `app/types/content.ts` | TypeScript interfaces for CMS documents (`BasePageData`, `LandingPageData`, …) |
| `outstatic/content/` | **The content itself.** Do not hand-edit unless you know what you're doing (see below) |

> `(cms)` is a Next.js [route group](https://nextjs.org/docs/app/building-your-application/routing/route-groups). It does not appear in the URL; it only lets the CMS have its own layout.

### Content folder layout

```
outstatic/content/
├── collections.json          # Registry of collections (currently: "pages")
├── singletons.json           # Registry of singletons (currently: "our-mission")
├── metadata.json             # Index of all documents, auto-generated by Outstatic
├── pages/                    # "Pages" collection
│   ├── schema.json           # Custom fields for this collection (welcomeMessage)
│   └── landing.mdx           # Document with slug "landing"
└── _singletons/
    ├── our-mission.md        # "Our Mission" singleton (status: draft)
    └── our-mission.schema.json
```

**Collections vs singletons**

- A **collection** is a list of documents of the same type (e.g. blog posts, events). Each document has a slug.
- A **singleton** is a one-off document (e.g. "Our Mission", "Site settings"). Singletons are new in Outstatic v2.

Each document is Markdown with YAML front-matter. Built-in fields are `title`, `slug`, `status` (`draft`/`published`), `publishedAt`, `author`, and the Markdown body (`content`). Custom fields are defined in the CMS UI and saved to the matching `schema.json`.

## Local setup

### 1. Create a GitHub OAuth app

You only need one per environment, and a maintainer may already have a dev one to share.

1. GitHub → **Settings → Developer settings → OAuth Apps → New OAuth App** (or create it under the `Happy-Homes-Community` org)
2. Fill in:
   - **Homepage URL:** `http://localhost:3000`
   - **Authorization callback URL:** `http://localhost:3000/api/outstatic/callback`
3. Copy the **Client ID** and generate a **Client secret**.

For production, create a **separate** OAuth app whose URLs use the production domain, e.g. `https://www.happyhomescommunity.org.uk/api/outstatic/callback`.

### 2. Environment variables (`.env.local`)

| Variable | Required | Notes |
|---|---|---|
| `OST_GITHUB_ID` | ✅ | OAuth app Client ID |
| `OST_GITHUB_SECRET` | ✅ | OAuth app Client secret |
| `OST_REPO_SLUG` | ✅ | `happy-homes-community-v2`. On Vercel it defaults to `VERCEL_GIT_REPO_SLUG` if empty |
| `OST_REPO_OWNER` | recommended | `Happy-Homes-Community`. If empty, Outstatic falls back to the logged-in user's GitHub username. Set it explicitly, since the repo belongs to an org |
| `OST_REPO_BRANCH` | optional | Defaults to `main` |
| `OST_CONTENT_PATH` | optional | Defaults to `outstatic/content` |
| `NEXT_PUBLIC_APP_URL` | optional | e.g. `http://localhost:3000` |

### 3. Log in

`npm run dev` → open <http://localhost:3000/outstatic> → **Sign in with GitHub**.

## The editing workflow (important)

Outstatic writes through the **GitHub API**, not your local disk. That has some consequences:

1. Saving in the CMS commits **directly to `main`** (or `OST_REPO_BRANCH`) on GitHub, even when you're running locally.
2. Your local `outstatic/content/` does **not** update until you `git pull`.
3. The website reads content from the **filesystem** (`outstatic/content/`). A deployed site only shows new content after it is **rebuilt/redeployed** from the new commit. On Vercel, a push to `main` triggers that automatically.
4. Because the CMS commits to `main`, **pull before you push** to avoid conflicts, and don't hand-edit content files on a feature branch that someone is also editing in the CMS.

To try schema changes without touching `main`, point a local `.env.local` at a test branch:

```bash
OST_REPO_BRANCH=cms-sandbox
```

## Reading content in code

All CMS reads happen in **Server Components** (no client-side fetching needed).

### A document from a collection

```tsx
import { getPageData } from "@/app/lib/contentParser";
import { LandingPageData } from "@/app/types/content";

const page = await getPageData<LandingPageData>("pages", "landing", ["welcomeMessage"]);
// page.title, page.content (markdown), page.welcomeMessage, ...
```

`getPageData` always fetches `title, publishedAt, status, author, slug, content` and merges in any extra fields you pass.

### Other helpers from `outstatic/server`

```ts
import {
  getDocuments,        // all docs in a collection:   getDocuments("blog", ["title","slug","publishedAt"])
  getDocumentSlugs,    // for generateStaticParams:   getDocumentSlugs("blog")
  getSingletonBySlug,  // a singleton:                 getSingletonBySlug("our-mission", ["title","content"])
  load,                // Mongo-style queries over metadata.json
} from "outstatic/server";
```

Example: published blog posts, newest first:

```ts
const db = await load();
const posts = await db
  .find({ collection: "blog", status: "published" }, ["title", "slug", "publishedAt", "coverImage"])
  .sort({ publishedAt: -1 })
  .toArray();
```

> `load()` reads `metadata.json`, so it only sees fields that Outstatic has indexed there.

### Rendering the Markdown body

`content` is a Markdown string. `react-markdown` is installed transitively via Outstatic but is **not** listed in `package.json` yet. Add it as a direct dependency before relying on it:

```bash
npm install react-markdown
```

```tsx
import ReactMarkdown from "react-markdown";
<div className="prose"><ReactMarkdown>{page.content}</ReactMarkdown></div>
```

(For `prose` classes to style anything, add `@tailwindcss/typography`. It is not installed yet.)

### Draft vs published

`getDocumentBySlug` / `getSingletonBySlug` return documents **regardless of status**. Filter on `status === "published"` yourself, or use `load()` with `{ status: "published" }`.

## How to move a page into the CMS (recipe)

This is the main outstanding work (see [`ROADMAP.md`](ROADMAP.md)). The general pattern:

1. **Decide the model.** Repeating items (blog posts, events, partners, team members) → a **collection**. One-off blocks of copy (mission, about page, contact info, site settings) → a **singleton**.
2. **Create it in the CMS UI** (`/outstatic` → Collections/Singletons → New) and add custom fields (string, text, date, image, tags…). Outstatic commits the `schema.json` and entries to GitHub.
3. `git pull` to get the new files locally.
4. **Add a TypeScript type** in `app/types/content.ts` for the document shape.
5. **Replace the hard-coded data** (e.g. in `app/data.ts` or the page file) with a call to `getPageData` / `getSingletonBySlug` / `getDocuments` in the page's Server Component.
6. **Handle missing content** gracefully (the helpers return `null` when a slug doesn't exist): call `notFound()` or fall back to a sensible default.
7. Delete the now-unused hard-coded data.
8. Open a PR (see [`CONTRIBUTING.md`](../CONTRIBUTING.md)).

### Images

Images uploaded through the CMS are committed to the repo (by default under `public/images/`) and referenced by path. Existing images in `public/` can keep being referenced by path (e.g. `/posters/picnic-poster.jpg`) from a CMS string field.

## Gotchas

- **Never edit `metadata.json` by hand.** Outstatic regenerates it. If it gets out of sync, open the CMS and re-save a document, or use the metadata rebuild option in Outstatic settings.
- **Renaming slugs** changes filenames. Update any code that references the old slug (e.g. `getPageData("pages", "landing")`).
- **Custom fields aren't validated at runtime.** If you rename a field in the CMS, update the TS interface and the code. TypeScript can't catch the mismatch for you.
- **Production login fails?** Check that the OAuth app's callback URL exactly matches `<domain>/api/outstatic/callback` and that the env vars are set in the hosting provider.
